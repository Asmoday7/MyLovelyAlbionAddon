# MASTER SPECIFICATION — Albion Trade Desk

## 0. Цель проекта

Создать полноценное локальное приложение для **экономической аналитики Albion Online**, ориентированное на личное использование на Windows, преимущественно на сервере **Asia (East)**.

Рабочее название: **Albion Trade Desk**.

Это не просто просмотрщик рыночных цен и не обычный калькулятор крафта. Это персональная бизнес-аналитическая система для принятия решений:

- Что выгоднее всего покупать, крафтить, улучшать и продавать?
- Какие предметы имеют достаточную ликвидность?
- Сколько единиц реально продаётся за 1 час, 24 часа и 7 дней?
- Какая прибыль остаётся после всех затрат и налогов?
- Где выгоднее покупать материалы и продавать готовые товары?
- Выгоднее продать предмет в обычном городе, Caerleon или Black Market?
- Как оптимально использовать капитал, Focus и производственные ресурсы?
- Какие торговые возможности являются устойчивыми, а какие возникли из-за случайных или устаревших цен?

**Основная цель — максимизация реалистичной прибыли с учётом ликвидности, затрат, времени оборота и риска.**

Проект должен быть бесплатным для личного использования, автономным, модульным, расширяемым и не зависеть от платных аналитических сервисов.

Язык интерфейса по умолчанию — русский. Названия предметов — на русском с возможностью переключения на английский. Внутренние идентификаторы Albion должны всегда сохраняться.

Все локации, серверы и качества должны корректно обрабатываться в каждой экономической модели.

## 3. Источники данных и сканирование

### 3.1. Albion Online Data Project REST API

Документация:

https://east.albion-online-data.com/api-docs

Использовать:

- `prices` — рыночные цены.
- `history` — исторические данные.
- `orderbook` — глубину заявок, если endpoint действительно предоставляет её.
- `charts` — исторические графики, если полезно.
- `gold` — статистику золота.
- Другие документированные методы по необходимости.

Прежде чем писать адаптер, проверить живые JSON-ответы.

Сделать поддержку:
- Batch requests.
- HTTP compression.
- Ограничений длины URL.
- Кэширования.
- Очередей запросов.
- Rate limits.
- Exponential backoff.
- HTTP 429 и RateLimit-Reset.
- Повторного использования полученных данных.

Не делать отдельный API-запрос на каждый предмет, если можно эффективно группировать запросы.

### 3.2. Локальное сканирование рынка

Это одна из приоритетных функций.

Сценарий использования:

1. Я запускаю Albion Online и официальный Albion Data Client.
2. Вручную открываю рынок в игре.
3. Перелистываю категории, предметы, страницы и фильтры.
4. Рыночные данные, которые получил игровой клиент, должны по возможности попадать в нашу локальную систему.
5. Приложение привязывает сведения к предмету, городу, качеству и времени.
6. Новые данные немедленно участвуют в расчётах.

Исследовать официальный проект:

https://github.com/ao-data/albiondata-client

Проверить параметр `-i` для отправки публичных данных нескольким адресатам, включая локальный HTTP-приёмник. Изучить точный формат сообщений и возможность одновременно сохранять стандартную отправку в AODP.

Рассмотреть архитектуру, аналогичную AlbionSnipe.

**Не разрабатывать собственный перехватчик пакетов, пока не проверена возможность использования официального клиента.**

Не автоматизировать игровой интерфейс, не делать бота, не внедрять код в клиент игры и не обходить защиту. Сканирование должно происходить при ручном просмотре рынка с использованием разрешённых источников данных.

### 3.3. NATS

Документация:

https://east.albion-online-data.com/developer

Изучить:
- `marketorders.deduped`
- `markethistories.deduped`
- Форматы сообщений.
- Дедупликацию.

Использовать NATS как дополнительный источник текущих обновлений, а не как гарантированно полную копию рынка.

### 3.4. Массовые исторические данные

Проверить возможность импорта ежедневных дампов AODP для Asia.

Нужна стратегия первоначальной загрузки большого объёма истории, чтобы не делать десятки тысяч одиночных запросов.

Если какая-то часть данных недоступна, не имитировать её.

### 3.5. Приоритет достоверности

Для каждого рыночного значения хранить:

- Источник.
- Сервер.
- Локацию.
- Item ID.
- Качество.
- Цену.
- Тип цены.
- Время рыночного наблюдения.
- Время получения нашим приложением.
- Возраст значения.
- Признак достоверности или ограничения.

Не смешивать наблюдённые цены, исторические средние и прогнозные цены.

## 4. Полный каталог предметов

Использовать:

https://github.com/ao-data/ao-bin-dumps

Не прописывать вручную тысячи item ID.

Импортировать:
- Все доступные предметы.
- Названия RU/EN.
- Внутренние ID.
- Категории и подкатегории.
- Тиры.
- Зачарования.
- Качество.
- Рецепты.
- Количество создаваемых предметов за производство.
- Материалы.
- Производственные особенности.
- Признаки расходников, артефактов и прочего.

Предусмотреть синхронизацию каталога после игровых обновлений.

Поиск должен находить предмет и по названию, и по ID.

Пользователь не должен видеть сырые ID вроде `T6_2H_STAFF@2` вместо нормального названия, хотя ID должен оставаться доступным.

Добавить избранное, категории, сохранённые фильтры, ручные подборки.

Иконки предметов необязательны, но можно реализовать их ленивую загрузку через публичный Albion Render API. Они не должны замедлять таблицы.

## 5. Главный модуль — Market Intelligence

Создать большую аналитическую таблицу со всеми доступными предметами и возможностью сортировки и фильтрации.

Обязательные параметры:

- Предмет.
- Tier / Enchantment / Quality.
- Категория.
- Город.
- Минимальный sell order.
- Максимальный buy order.
- Spread.
- Spread %.
- Объём продаж за 1 час.
- Объём продаж за 24 часа.
- Объём продаж за 7 дней.
- Среднесуточные продажи.
- Средневзвешенная историческая цена.
- Колебания цен.
- Возраст данных.
- Предполагаемая ликвидность.
- Признак аномальной цены.

Дополнительные метрики:
- Денежный оборот рынка за сутки.
- Динамика спроса.
- Глубина sell/buy, если известна.
- Соотношение объёма заявок и исторических продаж.
- Доля доступного рынка.
- Оценочное время продажи партии.
- Устойчивость цен за 7 и 30 дней.
